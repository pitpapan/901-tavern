# F3 最小状态、记忆与存档设计审阅稿

状态：F3设计审阅稿。普通游玩直接使用酒馆聊天、分支与摘要；配套 opening_seed.json 仅供作者核对开局与可选迁移，尚无实际游玩分支。具体导出与配置留到F4。

## 1. 原生功能优先，不另造存档系统

御临风使用酒馆原生 Persona 保存玩家身份与描述，并按需要绑定聊天。Persona 不是程序化的控制权限系统；避免主持代写御临风，只需保留简短明确的主持约定。本轮不另建主角控制系统，也不重写已有人物专档。[官方 Persona 文档](https://docs.sillytavern.app/usage/core-concepts/personas/)

分支和存档优先使用原生聊天、Create Branch 与 Create Checkpoint；二者都可复制截至指定消息的聊天，前者切换到新分支，后者保留在原聊天。迁移或备份优先导出原生 JSONL，保留聊天元数据；纯文本适合查阅，会丢失元数据。[官方聊天文件文档](https://docs.sillytavern.app/usage/core-concepts/chatfilemanagement/)

长期记忆优先使用默认附带的 Summarize：它能生成、保存、编辑及利用摘要，将摘要关联到消息，并提供 Restore Previous；删除或编辑附有摘要的消息时会回到上个有效摘要。本项目补充的是“摘要该记什么”的规范，无需让用户再维护一套 JSON。[官方 Summarize 文档](https://docs.sillytavern.app/extensions/summarize/)

普通对话由原生聊天记录承载，最近聊天承载场内增量；切场景或重要变化时整理短摘要，想保留分歧点时用原生检查点。Summarize 可以按前端配置自动更新，也可以在场景边界手动触发。无需每句话输出 JSON、额外创建 changes.md，或逐项请求用户批准状态。本轮只定内容规则，F4 再确认实际入口和加载位置。

本稿的 state 字段和 opening_seed.json 是作者结构化参考及可选迁移格式，不是额外常驻引擎。将来换前端，可把原生聊天导出和一份普通文本场景摘要带走；如作者确有需要，也可另存 state.json 与后台文件，但它们不构成普通游玩的必需步骤。

只有额外保存了前端之外的文件，才需要操作者同步其截至消息和版本。字段名不会自行给外部文件带来去重、秘密过滤或回滚。不要把这种额外同步责任误说成酒馆本身不保存聊天或摘要。

## 2. 最小状态内容与可选字段

以下是摘要内容的逻辑分区，可直接写成短段落；不要求用户填写表格。字段名只供作者结构化整理和未来迁移。

| 字段 | 保存内容 |
|---|---|
| header | 分支/聊天标识、依据的开局、截至消息和所选版本；可直接沿用前端标识。可选外部格式使用 branch_id、snapshot_id、seed_ref、through |
| scene | 当前地点、相对时间、确已在场者；精确日期没有来源时留空，不用帖子发布日期换算 |
| facts | 已成立、当前相关的客观条件；伤势、客观关系和发生过的结果可用同一条短记录表达 |
| knowledge | 逐个持有者的知道、相信、怀疑、明确不知或秘密；写明由什么见闻或消息取得 |
| resources | 只有会影响当前选择的物品、资源和客观状态；区分最后账目与此刻余额 |
| open_threads | 未履行承诺、未完成行动、少数当前相关的条件事件及数值缺口；计划和尝试不写成完成 |
| disclosures | 只保存对后续解谜/连续性重要的“已向玩家展示什么、在哪条消息、从哪个视角展示”；不复制整段对白 |

作者结构化记录至少保留短内容、certainty、适用时点和 source_refs；需要互相引用时才加局部 id。运行短摘要只需保留必要的出处定位，不必暴露字段名。本分支的新事实以保留消息为来源，不伪装成原团出处。局部 id 是查找键，不是新建正式世界书编号或类型。事实纠正时引用被替换的 id，保留历史记录；不同来源的冲突并列，不悄悄覆盖。

资源需要计算时才增补单位、持有者和当前值，不提前把每个 NPC 做成完整数值表。持久关系保存实际关系事件、客观关系与有来源的当事人态度，不创造好感度。角色稳定行为和世界法则仍按需引用既有档案，不反复抄入快照。

原团来源与本分支出处分别保存。重玩不是原 current_state.md 所描述的延续时点；其新结果只属于这个重玩分支，不能自动写进 Original Campaign Canon、Transition Canon 或 Continuation Canon。

## 3. 三层信息，分别更新

1. **世界事实**：什么实际成立。例如一封信确已发出，是一项事实；“信里说敌军撤退”不证明敌军真已撤退。
2. **谁已获知或相信**：谁收到什么版本，来自谁、通过什么渠道、何时收到；保存 knows、believes、suspects、does_not_know 或 secrets。被骗和误解可以影响行动，之后依据新见闻更新，不把旧误解追认成真。
3. **向玩家展示过什么**：消息中实际呈现的言行、线索和说明。展示作者后台不等于御临风亲历；某角色听到一句话，也不等于已向玩家展示说话者真实意图。

上述边界同时适用于御临风、每个 NPC 以及机构内部的人。某 NPC 知道御临风的事，必须有其见闻或消息来源；队友不共享全部知识，机构有人收到报告不等于全员同步。发送、送达和相信是不同变化，若只有发送证据就只记发送；渠道和耗时未知时保留未知，不编造固定传播速度。

certainty 沿用 confirmed、uncertain、rumor、character_belief。它表示该条内容的证据性质，与“谁持有”及“谁能看到”不同。例如“甲确实说了某话”可为 confirmed，话中命题另记 character_belief 或 rumor。knows 不授权模型把对应的作者事实整包加载给角色；secrets 也不保证秘密内容真实。

御临风的控制权属于用户：主持可裁定用户已声明尝试的成败、外部后果、受伤及非自愿生理反应；不能新增其对白、主动行动、内心、目标、态度或成长选择。保存摘要也不能把“考虑报信”改成“已报信”，把提问改成答应。对 NPC，主持依其模板、目标、所知和本分支条件作决定，不要求每个动作人工确认。

## 4. 空值和否定不是一回事

- value_state = unknown 且 value = null：明确保留“需要这个字段，但目前不知道”；不得当作 0、满额、无消耗、能力不存在或可任意使用。
- 字段未出现：这一快照没有记录/没有加载该项；不表示角色不存在、物品已失去或事件没发生。
- value_state = absent：有证据表明对象在此范围确实不存在或不在场；需来源，且标明范围。
- 已知布尔值 false：某个明确命题为否；例如不允许代写 PC 行动。它不是信息缺失。
- 空列表：当前未列出记录；除非另写“已穷尽的完整清单”，不承诺世界里没有其他人物、线索或行动。

首次使用到的数值若会决定交易或重大成败，才针对那一项查已有规则或给出简短桌外裁定。该次确定的新值注明由哪次约定产生；不倒写成原团原有数字。不涉及它的交流、观察与准备可以继续。

## 5. 什么时点整理摘要与建检查点

原生聊天正常记录消息。需要整理长期摘要或保留分歧点时，以实际场景和实质变化为依据；不另设每句话的人工保存流程：

- 离开地点、明显转移时间、场景收束，或准备结束本次游玩。
- 重要物品易手、伤势/关键资源变化、承诺成立或解除、身份与秘密被实际揭示。
- 持续外部行动发生阶段性改变，后续场景必须据此判断。
- 重生成旧消息、删除中段、分叉或换前端之前。

一次场景结算只整理一块短摘要：截至哪个保留版本、实际发生什么、哪些条件改变、谁新增/修正什么知识、哪些问题仍未定。可参照[摘要提示草稿](summary_prompt.md)，将它用于 Summarize 当前摘要，不再另抄相同日志。若作者另存了外部后台变化，才同步该文件；没有变化的不重抄。场景内快照之后的保留聊天继续有效，不能因为没保存就无视新伤势或已说出的承诺。

Summarize 的内容可遵循下列普通文本结构；没有相应变化的行直接省略，实际摘要不必逐行机械复现：

    场景/保存点：
    截至：消息定位 + 版本定位
    已成立结果：
    资源/关系/条件变化：原值或原状态 → 新值；依据
    知情变化：持有者；新增/修正内容；来源人及渠道；收到时点
    已展示线索：内容；消息；视角
    尚未解决：
    本次影响的后台记录 id：（仅引用，不在公开日志抄秘密）

不记录模型推理草稿或每个被放弃的战术选项。新发生且有持续影响的结果进入短摘要；日常寒暄留聊天。重要经历压缩后依然保留来源消息，后续按需回查，不把摘要当作比聊天更高的证据。

## 6. 候选、保留、重试与回滚

| 操作 | 状态处理 |
|---|---|
| 候选回复、推演备选、未完成的生成 | 不进入当前摘要或作为存档结果；其中的消耗、揭露、死亡或承诺均未成立 |
| 保留回复 | 用户继续承接这个版本、明确选择它，或保存当前选定版本，即可作为保留依据；无需再逐项问确认 |
| 技术重试 retry | 同一消息和同一版本的一次结果只记一次；重发保存请求不再次扣资源或再次发送消息 |
| 重新生成 regenerate / 切换候选 | 以本轮玩家声明之前的局面，加该声明重新裁定；不能把被弃回复的结果叠在新回复上 |
| 编辑玩家声明 | 只保留编辑后实际声明的内容；其后依赖旧声明的回复及结算需恢复到此前保存点再核对 |
| 删除或改动已保存的中段 | 回到其之前最近原生检查点，并使用相应有效摘要；需要继续后续内容时按仍保留聊天重建；不沿用来自弃稿的资源、关系、知识和后台进度 |
| 分叉 | 优先使用原生 Create Branch；后续变化各归各聊天分支，原分支留存 |
| 回滚 | 回到对应聊天与有效摘要；若额外维护外部后台/数值文件，一并恢复其相同消息位置 |

当前轮重生成时，若玩家声明没有变化，声明本身保留；其结果重新生成，不能据弃稿提前知道结果。日常使用沿用酒馆当前选中的消息版本。只有额外导出外部状态时，才需为它记录“消息 + 候选版本”的定位；不能用会随删帖变化的裸序号代表永久出处。

旧消息改变后，不强行保留与其冲突的后续对白和后果。先标出受影响范围，恢复前一检查点；仍有效的原有结果原样重建，不重新抽取已经保留的掷骰。真正重演的尝试再按已选规则处理并留出处。酒馆原生摘要有消息关联和恢复功能，优先使用它。切换候选后的摘要仍应对应实际所选版本；只有自定义外部文件才需要另外同步，不能假定前端会替外部文件回滚。

回滚改变角色与世界在该分支的状态，不可能抹去真实用户已读过的信息。弃稿可留在前端历史供查阅，但不进入当前上下文摘要；分支记录也不会回写或删除原团历史。

## 7. 有限上下文怎么用

按实际场景选取资料。以下为保留优先次序，不承诺固定 token 数，也不声称所有资料都已配置加载：

1. 简短主持边界、PC 控制规则、当前玩家声明。
2. 当前场景和快照之后的保留聊天；包括当前判断会用到的资源、在场者和知识边界。
3. 实际参与 NPC 的阶段片段、这次裁定直接涉及的世界规则和已成立条件。
4. 相关的重要经历、承诺和少数正在起作用的外部行动。
5. 只有裁定确实需要时，选取最小后台事实；作者完整档案和原团未来历史供查证，不整体输入。

预算不足时先移除离场人物、无关历史和重复文字，再压缩已结算经历；不能挤掉 PC 边界、目前关键未知或直接影响成败的规则。短场景摘要与完整快照不重复整包加载。source_refs 常留查阅层，提示中仅带必要引用标识；出现事实争议再打开具体原文，不全库重读。

梦境默认不加载。原团后期成长与结局不做后续清单；同伴只按已有模板及本分支实际时间、条件成长，不创造经验公式或自动领取原线奖励。布莱特具体终局不进入任何运行记忆。主神/幻剑旧机制不重新启动。

author_only 是资料选择边界，不是加密或模型权限系统。opening_seed.json 把后台单列供人审阅，因此整份种子也不得直接贴进前端。将来需从审阅种子择取场景部分；幕后条目只有在裁定相关时另选必要片段。同一请求里一旦提供秘密，就仍有误泄露风险，不能靠字段名保证绝对隔离。

## 8. 种子范围与轻量检查

opening_seed.json 保存首次入都的已证锚点、最后钱药账与现存缺口、最少在场人物状态、有限知情及隔离的作者后台。每条开局断言都带本地研究或澄清出处；source_index 指向本地文件和行号，研究记录内继续保留原帖定位。引用研究稿不等于重新宣布其成为正式正典。

高塔双潮与白魔脱困是 T0 前史，不设为未来等待触发事件；悠悠的责任理解保留为她本人的信念，不等于她知道咒术全貌，也不传播给御临风或其他 NPC。医馆和守门军官的隐藏背景不自动变成入城知识。

场景摘要出现实质变化时，仅快速核对四件事：截至版本是否正确；PC 是否被代写；实际变化及未知是否保持；秘密和收到消息的人是否对应。只在有实质问题时回查，不建立逐轮全库验证或大型测试矩阵。本轮对种子只检查 JSON 可读、局部引用可定位及明显边界错误，不做实际模型测试。
