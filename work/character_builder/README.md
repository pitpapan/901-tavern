## 输入和调用

`buildCharacter(definition, initial, { existingState } = {})` 返回 `{ok, state, report}`。定义必填稳定 `id`、`name`、`period`、非空 `sources`、`size`、六属性，以及有明确数值的 `skills`。子技能嵌在所属主技能下，写 `level` 和适用 `scope`；主技能等级最多 5，子技能无额外上限。反射和强韧计算需要明确的 `运动`、`求生` 主技能等级；确为零时写 `0`，不能用遗漏表示零。检定前调用 `requireKnownSkill(state, main, sub)`；多个子技能可能适用时，由调用方选定一个，Builder 不猜测或相加。

`initial` 必填 `health`（完整 B/L/A 槽对象，或示例明确选择 `"healthy"`）、`willCurrent`、`turn`（PHB 动作对象，或示例明确选择 `"ready"`）。资源池须在定义中有已确认上限，并在 `initial.resourceBalances` 中给当前余额。可给 `xp`、`statuses`、`attributeDamage`、`greatPowersAvailable`；构筑不补发历史 XP、节点奖励或大能选择。已存在存档应直接使用当前状态；传入 `existingState` 会拒绝重新初始化。调用者负责存档生命周期和持久化。

`overrides.derived[field]` 写 `{mode:"base"|"final", value, source}`。`base` 先取已确认异式基础值再加适用资源加值；`final` 是已含加值的最终卡面值，不再叠加。`attributeAuto` 与技能 `auto` 覆盖值写 `{value,source}`，已存卡面自动成功由来源保留，不和等级门槛重复计算。未指定时沿内核门槛计算。`power_reference` 只原样传递，不参与数值或合法性判断。

按需在现有叙事说明或 `abilities` 描述中，用几句话写明已确定的训练与实践来源、主要擅长领域、邻近领域的一般实践能力及已知明确限制；普通人物可共用说明，重要人物再个性化。未确定的领域可不写，不为填满说明编造经历、专长或“不可能做到”的限制；不逐项枚举法术、法阵和生活技艺，不强迫原创能力或追溯一生 XP。此说明与既有属性、主／子技能、资源引用及最终数值并存，不代替它们；来源存在、901 采用、人物取得和引擎支持仍分别核对，未授权资源的专有机械收益不能改称隐含能力取得。不新增必填字段，执行仍受现有接口支持范围限制。

## 资源撰写模式

定点读取流程见 [资源撰写入口](resource_authoring/README.md)：常用融合规则卡、特性预算速查、定标样板与完整来源库检索。按任务读取相关部分，同批不重复通读。RE 旧称“称号／训练”现统一为“能力组”，旧称仅保留作检索别名；普通主／子技能与资源类“技艺”分别处理。

仅在明确授权的资源创作、人物构筑缺项或成长方案设计中按需读取本节；普通技艺仍可按已确定的能力范围临场裁定，不为每种用法制作资源，也不把本节注入逐回合 GM 提示。适用于能力、法术、特性、能力组、成长书和装备。正式资源须说清实际增加的能力；不能为维持购买价值而剥夺其他角色合理的基础操作。玩家与 NPC 的资格和效果边界采用同一原则。

1. 先明确设计用途、适用对象及希望增加的实际能力。
2. 只查少量直接相关、已采用的资源及 RE 同类条目，判断可否复用、组合或适配，并记录比较依据；效果强度以 RE 为基准，训练等机械型特性参照 RE 专长，扮演型角色特性参照 RE 角色特性，不混用两类效果。不要从资源库缺项推断能力绝不可能存在。
3. 确需原创时，可以提出效果与必要数值的原创候选，明确标记原创，不伪造原书来源；不要求所有能力都数值化。
4. 按下列条目写出可审阅草案，标明未决校准和执行支持缺口。草案不自动获得 901 采用、人物取得或 XP 支付；沿用现有采用、取得、适配流程，不增设审批层级。

**条目模板（只保留适用项）：**

- **名称／类型／身份：**能力、法术、特性、能力组、成长书或装备；引用来源或标为原创候选。
- **用途与对象：**解决什么问题、谁可使用；写明实际新增效果、能力范围及必要数值，不以空泛概况代替效果。
- **运作与限制：**使用条件、动作、消耗、持续时间、次数／范围及明确限制；无关字段省略。
- **取得与价格：**取得条件；需要定价时给出 XP 价格候选及与相关已采用资源的比较依据，不追溯人物一生的 XP。
- **资源关系：**可否叠加、互斥、重复取得，以及与已有资源的交互。
- **校准与支持：**来源或原创标记、比较依据、待决定的强度／价格问题、当前引擎可执行部分与未支持部分。

成长书另说明各阶段收益；能力组说明取得条件与阶段收益；装备分开写物品本身效果与使用者资格。设计可成立而引擎尚不支持时，保留候选和缺口，不标为已可执行；未授权资源也不能换名为隐含能力取得其专有收益。

`resources` 各项需 `id`、`source`、`adoption`、`engineSupported`。采用状态为 `ADOPTED` 或 `CONFIRMED` 且引擎支持时，才解析 `hpBonus` 与 `derivedBonus` 数值效果，以及有明确上限和初始余额的资源池；同一资源 ID 或同源效果 ID 重复即报错。其他效果、能力，以及标记 `engineSupportStatus: "UNSUPPORTED"` 的装备保留在状态与 `report.unsupported` 中。当前操作依赖其 ID 时先调用 `requireOperationSupport(report, ids)`，否则只使用已可结算部分。`state.resourceRefs` 只保留 ID、出处、采用／取得记录、前提状态和实例状态，不保留效果参数；运行时参数必须由可信资源目录重新取得。普通武器、物理 DR 和骰序由调用方按现有内核接口明确传入，不建立资源规则脚本或自动推断装备效果。

Builder 调用内核 `createCharacter`、`effectiveSkill` 取得基础角色与技能值；输出 `state` 可直接交 `beginTurn`、`check`、`resolveAttack`。它补算规则已确认的反射与强韧，保留已确认覆盖和初始余额；不复制攻击、伤势或成长算法。`report` 列出错误、缺项、未适配项、覆盖来源和已计算字段。内核返回的新状态才是本分支之后的当前状态。

## MVU 对应与边界

Builder 的 `state` 与现有 PoC 的 `actors[id].state` 形状对应；外层 `schemaVersion`、`revision`、`chatId`、`operations` 仍由 MVU 适配层负责。Builder 不触碰 `stat_data` 或适配器。其初始化只用于新存档，不能覆盖现有存档的伤势、资源、XP、成长和行动使用情况。大能待选数只保存已明确数值，不自动选能力。资源的作者采用和规则适配状态独立，未适配能力不能据一次普通攻击成功宣称已全部可运行。内核成长保留最终卡面覆盖，并按 `derivedBaseOverrides`、`derivedBonuses` 维护已接入的基础覆盖和数值加值；新资源效果仍须单独适配，不能将 Builder 再作用于已有存档。
