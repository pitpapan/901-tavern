# 御临风重玩中的剧情推进与酒馆运行设计

这份补充说明资料整理完成后，AI 怎样从“知道世界和人物”走到“主持一段可以改变的故事”。首版采用一个主持模型，综合世界约束、NPC 当下处境、玩家行动和本分支状态决定后果。酒馆负责组织和发送所需资料；每轮剧情判断由接入的模型完成。

状态：设计提案，补充原规划第七至九节。本轮未开发酒馆脚本、导出正式卡或进行实际游玩测试。以下流程与结构是运行设计；假设例子不属于原团事实。既定事实与独立行动按用户确认保留，额外无条件锁定未来结果尚未提出。

## 1 剧情从哪里来

世界书给出可依赖的背景和限制；人物档案给出行为依据；当前状态说明此刻已经发生什么；事件资料说明什么条件下可能有变化。AI 将它们和御临风本轮的行动一起使用。

| 输入 | 参与剧情推进的方式 | 必须避免的混淆 |
|---|---|---|
| 世界与力量规则 | 决定某种行动能否成立、代价和限制 | 有魔法不等于能临时创造任何法术 |
| NPC 的目标、性格、关系、知识与资源 | 决定此人此刻为什么行动、会考虑哪些办法 | 一次行为不是永久性格；主持知道不等于 NPC 知道 |
| 当前局面 | 决定谁在场、谁能介入、时间和资源如何变化 | 计划、传闻和行动成功不是同一状态 |
| 条件事件与势力行动 | 提供随世界内时间、消息和选择变化的外部压力 | 原团的下一幕不是本分支必须出现的下一幕 |
| 用户选择的固定节点 | 约束事先约定的发生维度 | 固定危机出现不等于固定御临风到场或失败 |
| 玩家实际输入 | 提供御临风选择的动作、话语和目标 | 模型不得补写用户没有选择的后续行动 |

重玩允许产生新的行动、对话和结果；这些属于新分支。资料缺少某人的秘密忠诚、身世、力量来源时，不能为方便剧情把空白补成“原来如此”。新战术可以依据已知目标产生，新的永久背景则留待获准补充。资料研究库继续遵守“不编造正典”。

## 2 每轮实际运行

~~~mermaid
flowchart LR
    A["玩家声明行动"] --> B["加载当前局面和有关资料"]
    B --> C["裁定直接后果及 NPC 反应"]
    C --> D["推进有条件的外部行动"]
    D --> E["呈现可观察的新局面"]
    E --> F["保留的回复进入本分支记录"]
    F --> A
~~~

一次普通回复只推进到下一个有意义的选择点，不把完整章节一次演完。上述过程是主持职责，不要求输出内部推理、推演草稿或大量状态面板。

1. **承接输入。** 区分已声明动作、尝试、提问与桌外讨论。人物讨论某个计划不代表已经实行；用户停顿不授权模型替御临风选择。
2. **读取当前相关资料。** 核对分支、地点、在场者、已知事实、可用能力与资源。只引入会影响当前判断的人物和规则。事实未知时保留未知。
3. **处理直接后果。** 明显且无争议的行动直接处理；有对抗、资源消耗或重要风险时，按已选择的规则裁定。若数值检定确实必要，使用可记录的实际掷骰或约定判定，不让语言模型声称进行了未执行的随机投掷。规则缺口若决定重大成败，先给出简短裁定选项，不能伪称原团已有规定。
4. **让有关 NPC 作出反应。** 用“有证据的当前目标＋此人所知＋性格与关系＋能力资源＋当前约束”决定行动。NPC 可以主动提议、拒绝、等待、撤退或改变手段，不必等待玩家点名；但不能代替御临风同意或完成其动作。
5. **推进当前相关的外部行动。** 只有已成立的行动、经过的世界内时间及消息传播支持变化时才推进。对话五条不等于时间过了五小时；远处人物不能瞬间获知现场秘密。没有条件满足时，安静交谈、旅行或准备本身也可以成为剧情。
6. **给出可观察结果和下一行动空间。** 呈现声音、行动、对话、已揭示线索和直接代价，在需要御临风决定的地方停下。无需每轮强塞战斗、反转或三选一菜单。
7. **保存保留分支的变化。** 只将实际保留的回复及用户明确行动记入本分支；重生成的弃稿、未实施的计划和候选后果不入账。状态摘要必须标明截至哪条消息，后面的聊天增量仍是当前场景依据。

## 3 把原剧情转成条件与因果

阅读原团时新增关注“当时为什么发生、谁实际知道、前提被改变会影响什么”。先记录来源明确的前后关系；没有证据的因果不补全。每个重要事件或势力行动按需保存下列信息，不给每个日常动作建节点：

| 字段 | 具体内容 |
|---|---|
| 来源与适用时期 | 原帖引用、原线历史时期、是否有开局已成立的证据 |
| 行动者与依据 | 谁在做事，已证目标和权限是什么 |
| 前提与阻断因素 | 需要哪些资源、在场人物、情报和机会；什么会取消或改变它 |
| 时间与消息 | 时间窗口或相对顺序；谁通过何种渠道才会得知 |
| 可观察影响 | 当前角色可能看到的线索；后台变化不自动旁白泄露 |
| 状态 | 尚未具备条件、可发生、进行中、已发生、受阻或取消 |
| 固定维度 | 仅填用户已经选定的部分；其余保持可变 |

只维护当前阶段有关的少数行动。势力目标缺证时，不补造整个战略；只让已有现场处境支持的局部反应发生。资源、消息、路线或时间未知时，不凭“模拟世界”把它们偷偷精确化。

**原线证据例子。** 帝都军官在 #88/msg816667 引用达卡斯的胜利报告；御临风在 #90/msg816671 激动反驳，#92/msg816677 后有押人命令。原帖提供的是一次具体信息冲突及处置过程，不能据此认定所有报信方式都会得到同一结局。出处见[入城原帖研究](<C:/Users/pit/.codex/worktrees/yulinfeng-tavern-plan/TRPG outputs/work/replay_research/opening_scene_evidence.md>)。

**人物关系补证。** 用户提醒该军官与达卡斯有关，随后回查 #86/msg816660、#141/msg817008：主持明确指出，后续跟在达卡斯身后的就是此前守城队长，他在场旁观栽赃。原例仅讨论现场军情冲突，遗漏了这一关系；不能把军官默认成中立的误信者。具体效忠等级、入伙时间和知晓内情仍未确认。详见[帝都世界证据](<C:/Users/pit/.codex/worktrees/yulinfeng-tavern-plan/TRPG outputs/work/replay_research/capital_world_evidence.md>)。

**仅作假设的重玩分支。** 如果你决定平静报告亲见事实并请求核实，模型仍须先读取该时期已核实的人物关系、任务与利益，再判断阻挠的手段和现场风险。更克制的表达不自动解除已有利益冲突，也不保证避免监视、拖延或追查；具体哪种反应成立，仍待完整资料和本次行动裁定。若你不去报信，办公室交涉本身没有现成触发前提，但有独立依据的其他行动并不因此消失。不能照搬每一步原线，也不能把改变语气写成改变阵营。

因此后续不预写每条选择分支，而是整理可复用的事实、行动依据、事件条件与结果依赖。剧情走向由这些条件在新分支中的实际变化产生。

## 4 既定事实与事件条件如何起作用

既定关系、开局前历史和有来源的势力行动按已明确事实保留。高塔遭袭与白魔脱逃不会因为御临风换一条路线就自动取消；帝与哈克本为兄弟，情感交易是御临风过去已经发生的经历。

已按这些原则整理的事件资料见[重大事件的发生依据与选择影响](<C:/Users/pit/.codex/worktrees/yulinfeng-tavern-plan/TRPG outputs/work/replay_research/event_causality_overview.md>)。各事件分别保留NPC行动依据、玩家参与、时间与资源条件、知情传播，以及原团已经发生的结果。不要将原团所有未来事件统一停住等待玩家，也不要强迫玩家重演原团参与方式。

- 相关原因和条件仍成立：其他人物与势力继续自身行动，不以御临风在场为前提。
- 新选择实际改变了条件：只重新判断受影响的过程与结果，说明所依据的变化，不凭空制造替身或巧合恢复原结局。
- 资料仅记录口供、预测或承诺：保留其说话者和证据边界，不自动转成成功结算或全知信息。
- 另行约定的无条件结果：只有用户明确提出时才单独记录。目前没有额外要求未来死亡、胜负、玩家决定或成长无条件发生。

上述内容是持续使用的资料边界，不构成每轮确认流程。原团后期能力获得事件只作历史和因果参考；御临风开局后的成长由用户重新选择。

## 5 在酒馆里怎样落地

SillyTavern 的 World Info 会把激活条目的内容加入提示词，提供背景；它不保证模型照做。它的消息延迟、持续等效果按消息计算，不能直接充当剧情日期或任务状态机。这也是本项目需要显式保存局面和事件条件的原因。[World Info 官方文档](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

第一版采用单主持卡。御临风使用用户 Persona；其他人物从作者档案生成阶段片段，由同一主持模型区分扮演。以后需要独立对话体验时再加独立人物卡，不让多张卡各自维护一份互相漂移的世界状态。

| 放置处 | 保存内容 | 初版怎样更新 |
|---|---|---|
| 主持卡及适用提示词 | 控制边界、裁定步骤、NPC 反应原则、只输出可观察后果 | 内容审核后稳定保存，避免每轮加长 |
| 御临风 Persona | 起点身份及适用连续性 | 阶段变化时更新；不是替玩家控制行为的指令 |
| 按时期导出的世界书和 NPC 片段 | 当前地区、人物、力量及已允许使用的背景 | 名称触发；关键在场资料纳入当前场景包 |
| 当前聊天的短场景说明 | 分支、时间、地点、参与者、关键资源、当前约束和截至消息 | 开场、切场景或关键状态变化时更新 |
| 主持事件资料 | 当前可发生的条件事件和最少的后台信息 | 切场景及重大条件变化时更新 |
| 分支摘要与聊天记录 | 本次已经发生的结果、承诺、未决线索及知情变化 | 场景收束时生成短摘要，原聊天保留回查 |

Author's Note 可按指定位置和频率插入当前聊天的短说明；它提供输入位置，不会自行决定剧情状态。本项目可用它放简短的场景提示，完整状态留在分支记录。[Author's Note 官方文档](https://docs.sillytavern.app/usage/core-concepts/authors-note/)

**无脚本时的最低可运行方式。** 普通对话由主持模型正常回复，最近聊天承载场内增量；切场景或关键变化时生成一份短结算，将它保存到当前聊天的状态说明。无需每轮手工重填全部人物表。摘要只记已发生的结果，不把 NPC 计划或御临风猜测写成完成事实。自动摘要有漏项和幻觉风险，因此关键物品、关系变化与未决承诺不能完全依赖自动摘要。[Summarize 官方文档](https://docs.sillytavern.app/extensions/summarize/)

**轻量辅助的后续实现。** 内容稳定后，可增加“保存当前场景”“载入阶段资料”“恢复上一存档”等少量操作。STscript 提供当前聊天的局部变量和世界书读写能力，可作为接入点；但结构化结果解析、分支存档和回滚一致性仍需本项目实现，不能假定添加几个自定义字段便自动生效。只更新专用重玩状态，绝不让脚本重写来源、人工审核候选或正式正典。[STscript 官方文档](https://docs.sillytavern.app/usage/st-script/)

第一版不要求多模型分工。更严格的秘密隔离或自动后台模拟如确有体验需求再扩展；本轮没有安装插件、连接 API 或承诺现有酒馆已具备这些功能。

## 6 状态与上下文如何长期接续

**梦境在默认导入内容之外。** 现有梦境原文与研究资料继续保存在作者档案，默认运行包不含梦境世界书、梦境人物卡、梦境剧情摘要或奖励表。以后明确要求体验时，再单独制作相应包。本项是F阶段的导出约束；当前尚未生成或安装酒馆导入包。

具体落实如下：

1. 默认包只从已审的主世界事实及适用时期状态中选取内容，不把整个研究目录、原帖文件或人物全时期档案直接打包。混合主世界与梦境的同帖按具体段落选取，不能整帖或整文件一并放入。
2. 梦境世界书不随主世界包提供，也不绑定全局、主持卡、御临风Persona或当前聊天。主世界人物卡内不嵌入梦境世界书，不把同名梦中角色的履历、对白或技能合并到主世界人物。
3. 默认包的角色描述、场景、开场白、示例对白、主持提示、作者注与记忆摘要均不夹带梦境叙事。不依赖一句“请忽略梦境”来抵消已经送进模型的长资料。
4. 若后续采用向量检索或其他资料检索，默认检索来源同样不包含梦境档案和整套原帖目录；只索引当前允许使用的主世界运行内容。这样也避免关键词、递归触发或同名相似度把梦域内容带入。
5. 开局已经成立或本分支实际发生的主世界影响，可以单独保留简短事实及证据归属；这是经过选取的主世界状态，不附完整梦中经历，不自动继承原团后期奖励。
6. 正式导出时核对默认包的内容清单，并在既有G阶段的一次提示词检查中确认实际发给模型的内容。不再增加每轮验证或完整重读。

依据：酒馆会组合全局及角色、Persona、聊天关联的World Info内容，角色主世界书还可以嵌入导出的卡；条目可由关键词、常驻或向量相似度激活。因此此处采用“默认导入内容不含梦境”的安排。[World Info官方说明](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

**将旁线证据统一编入背景设定与人物档案。** “沐透线”“大墓地线”只表示资料出处，不作为酒馆的加载单位，不制作独立旁线剧情包。已有世界、人物和事件研究继续共用同一套主题与实体编号；同一事实归并，原帖出处保留供作者查证。

| 从原记录提炼的内容 | 统一归入的档案 |
|---|---|
| 帝国行政、地方传信、救护、研究所与军部合作 | 背景设定集中的制度、组织、地点和概念主题 |
| 安兹势力的目标、资源、代理人、保密与通信方式 | 纳萨力克势力档案及相关人物、概念条目 |
| 沐透、安兹及其他人物的身份、背景、关系、能力与性格证据 | 各人物共用的作者档案，后续生成适用时期的NPC运行片段 |
| 有持续影响的历史事件与已启动行动 | 对应事件、组织或人物的历史和状态；保留时间、实际成果及知情范围 |
| 原线对白、逐场过程与未演完的后续 | 作者来源档案，供定位与考据，不作为运行剧情包 |

酒馆按背景主题、地点、人物及当前事件取用内容，不需要知道某条资料来自哪条故事线。完整背景设定集也按主题分条导出，不每轮整本载入。同一人物不会因分属主线、沐透线或大墓地线而生成多份相互漂移的运行档案。

并入背景不改变事实的有效时期：后来才发生的事不能前置到开局，人物获知时间另记。离场NPC与势力仍按有证据的条件行动；原线未完成的研究、传信和任务不补造结果。

两条旁线的主要阅读和证据归并已完成，背景模型与人物档案已有相应增量。后续复用这些成果，按已定正式编写流程整合主题，不再另起整线重建。`event_causality_sides.md`等文件保留为作者研究索引，不直接导入酒馆。

每次请求的重点是：短主持规则＋御临风适用信息＋当前状态＋在场 NPC＋相关背景及条件事件＋近期聊天＋压缩后的重要经历。完整作者库供查证，不整体塞入每轮上下文。正式世界书触发词仍限正式名、常用简称和已确认别名；事件开关和状态字段属于运行资料，不伪装成新的正式条目类型或泛用触发词。

状态至少能回答：这是哪个分支、记录到哪条消息、现在何时何地、谁在场、什么已发生、什么仍是计划、关键物品/伤势/承诺有什么变化、谁通过何事获得了新知识。持久关系记事件和当前态度，不强行赋予无来源的好感度数值。

主持需要某个秘密才能裁定时，才加载该秘密的必要部分并明确知情归属。同一次模型请求内没有严格的角色秘密隔离保证；预先隔离无关未来资料比“把全部剧情给模型再要求保密”更容易控制。这个设计降低提前泄露风险，实际效果仍须在适配时检查。

重新生成、删除或分叉聊天后，存档必须与实际保留消息一致。未来辅助脚本需要保存消息关联的快照；聊天局部变量本身不能被假定会随所有编辑操作自动正确回滚。无脚本时使用场景检查点恢复，不把弃稿结算叠加到新回复上。

## 7 补入后续交付的具体成果
